Question: what's up with putting commas after lists in tuples when there's no next element? Looks a bit weird.


## 🤖 Assistant

That's the **one-tuple marker**, and it predates the list sugar — it's the §4 convention used throughout (`(Tick,)`, `(Stop, 0)`'s sibling `("Print",)` in the toy example, etc.).

The reason: in expression/action position, parentheses are ambiguous between *grouping* and a *tuple*.

- `(n + h)` — grouping around an expression
- `(x,)` — a 1-tuple containing `x`

Since `parenExpr` treats a lone expression in parens as grouping, the trailing comma is the only way to say "tuple with one element" there. So in the example:

```
{ ([3, 1, 4, 1, 5],), (Total, 0) }
```

the initial state is a 1-tuple *containing a list* — `([…],)` — plus `(Total, 0)`. The comma isn't "after the list because there's no next element of the list"; it's after the list because that tuple has exactly one element (the list). Drop it and `([3,1,4,1,5])` parses as parenthesized grouping, not a tuple, and the machine patterns would never match.

The odd-looking asymmetry: **patterns don't need it** — that's why `--parse` renders `((h, t)), (Total, n)` with no trailing comma. Pattern position has no grouping form (`(p)` unambiguously means a 1-tuple pattern), so the comma is only load-bearing on the construction side. The pretty-printer exploits that: it emits the comma only where the round-trip requires it (`renderExpr` for 1-tuples, not `renderPat`).

If it reads as too weird, the alternatives are:

1. **Status quo** — Python-style `(x,)`, only in expression position.
2. **No grouping at all** — parens always mean tuple; expressions like `n + h` go bare. Big breaking change, loses `(a + b) * 2` style clarity.
3. **Different bracket for tuples** — e.g. `{…}` is taken by bags/initial blocks; would be a real grammar redesign.

I'd leave it — it's consistent, load-bearing, and documented in `Syntax.hs`'s round-trip note. But if you want to flip the design (it's a §4 question, not an §11 one), it'd be its own slice.
